# Post-Incident Review: Records Dropped at Boundary Timestamp

## Summary
Records with timestamps at the exact upper boundary of the reconciliation window were being silently dropped, causing `records_processed` to report 0 instead of the expected 150-400. This violated ADR-0001 (inclusive bounds on both ends) and was introduced by a revert of the boundary-condition fix. The root cause was a single character in the filtering logic: `<` instead of `<=` on the upper bound. The fix restored the inclusive upper bound.

## Timeline (UTC)
- 2026-08-19 09:01:05 — Metric anomaly detected: `records_processed` at 0 instead of 150-400
- 2026-08-19 — Commit 9964728 (revert of PR #4) identified as cause
- 2026-08-19 — Fixed upper bound in `GetRecordsForWindow` from exclusive to inclusive

## Impact
The nightly reconciliation job was dropping entire batches of records because vendor exports timestamp all records in a batch at the window's upper boundary. With an exclusive upper bound filter, no records were returned. This would cause reconciliation failures and incorrect financial reporting.

## Root Cause
In `app/src/ReconciliationJob/RecordStore.cs` line 36, the `GetRecordsForWindow` method used `r.TimestampUtc < toUtc` (exclusive upper bound) instead of `r.TimestampUtc <= toUtc` (inclusive upper bound). This violates ADR-0001, which specifies that all date-range queries must use inclusive bounds on both ends.

The vendor's batch processing model means all records in a nightly batch share the same UTC timestamp, which lands exactly on the window's upper bound. Using an exclusive bound silently drops the entire batch.

## Detection
Automated metric monitoring detected `records_processed` at 0 when historical range is 150-400 at 2026-08-19 09:01:05 UTC.

## Resolution
Changed line 36 in `RecordStore.cs` from:
```csharp
.Where(r => r.TimestampUtc >= fromUtc && r.TimestampUtc < toUtc)
```
to:
```csharp
.Where(r => r.TimestampUtc >= fromUtc && r.TimestampUtc <= toUtc)
```
